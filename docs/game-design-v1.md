# 게임 설계 분석 v1

> 원본: 사용자 제공 엑셀 로직 정리 파일 분석 결과 (Sheet1, Sheet2)
> 버전: v1 (최초 정리) — 이후 이미지/추가 자료 반영 시 v1.1, v1.2 …로 갱신

## 1. 핵심 컨셉

타일 기반 그리드 위에서 움직이는 실시간 대전 액션 게임.
플레이어는 항상 타일 정중앙에 위치하며, 이동/전투가 프레임 단위로 정밀하게 제어된다.

## 2. 이동 로직

- 타일 크기: 1x1 유닛 평면 타일
- 플레이어는 항상 타일 정중앙에 위치, 인접 8칸(상하좌우 + 대각 4방향) 중 하나의 타일 중앙으로 이동
- 이동은 순간이동이 아니라 lerp(보간)로 약 10프레임(개발자 설정 가능) 동안 진행
- 사방 이동과 대각 이동은 실제 거리가 다르지만(대각은 √2배) 소요 프레임은 동일 → 체감 속도는 같음
- 기본 이동속도: 10f(프레임)에 한 칸 이동 (캐릭터마다 다르게 설정 가능, 예: "나" 속도3, "적" 속도10f)
- 대각 이동은 두 방향키가 **6프레임 이내**에 함께 입력되면 하나의 대각 입력으로 판정
- **입력 잠금**: 한 번 이동 명령이 내려지면 다음 타일 중앙에 도착하기 전까지 추가 입력은 무시됨
  - 이동에 걸리는 프레임 수(기본 10f)가 곧 "연속 입력 가능 프레임"을 결정 (예: 8f 이동이면 9프레임째부터 다음 입력 가능)
  - 개발자가 이 프레임 수를 조정 → 캐릭터별 이동 속도로 활용
- 같은 방향키 2번 연속 입력 → 대쉬(2타일 이동)
- 대각 이동 시 스프라이트 각도를 45도로 틀어서 표시
- 이동과 애니메이션은 별개로 동작 (이동 로직과 스프라이트 표시가 분리된 시스템)
- 이동 프레임과 공격 프레임은 별개로 작동 — 이동 중에도 공격 가능, 피격 가능

## 3. 전투 로직

### 핵심 아이디어: "명령/지시" 은유
공격은 상대에게 특정 경직·스프라이트 상태를 강제로 요구하는 "명령"으로 설계됨.
- 공격자가 상대에게 "이 스프라이트로 변화하고, 이만큼 경직하라"고 요구
- 피격자는 (무방비 상태라면) 그 요구를 그대로 이행
- 동시 타이밍이면 서로가 서로의 요구를 받는 구조

### 판정 시스템
- 히트박스(공격 판정) / 허트박스(피격 판정) 분리
- 히트박스는 시전자 위치 기반으로 생성, 몇 프레임 동안 유지되는지 설정
- 판정 범위 내에 상대가 위치했는지로 히트 여부 판단

### 우선순위 판정 ("주심/부심" 비유)
- 동시에 서로를 공격했을 때, 공격 발생 시점을 비교해 우선순위 결정 ("주심"이 판정)
- "부심"이 공격 발생 시점과 기술 데이터를 전달하는 역할로 비유됨
- 더 빠른 공격이 우선 적용, 느린 쪽에는 강제로 "이동 지배자"(피격 반응) 활성화

### 기술(스킬) 데이터
기술마다 아래 스펙이 다르게 설정됨 (기술표/데이터베이스로 관리):
- 발생 프레임(선딜)
- 경직 시간(후딜)
- 효과 (스턴 / 밀치기 등)
- 위치 고정 여부
- 기술 코드 (예: s1, s2, 커스텀)

확인된 기술 예시:
| 기술 | 프레임 | 위치 | 효과 |
|---|---|---|---|
| 기본공격 | 7프레임 | 위치고정 | 스턴 |
| 밀치기 | 7프레임 | 위치고정 | 스턴 + 뒤로 1칸 넉백 |

### 기타 전투 규칙
- 이동 중 공격/피격 가능 (이동-공격 프레임 독립)
- 점프, 앉기 동작 존재
- 점프와 공격은 동시 입력 불가
- 치명타 기준: 데미지 50 이상
- 60프레임/초 기준, 경직시간·공격시간 등은 캐릭터 간 공유되는 프레임 단위로 계산 (기술별 발생/후딜은 다름)

## 4. 상태 머신 (FSM)

Player 본체 → PlayerStateMachine이 행동을 상태로 관리. 상태는 항상 하나만 존재(동시에 Idle+Move 불가).

```
[IdleState] --입력--> [MoveState] --이동완료--> [IdleState]

[Idle] → [Move]
           ↘
        [Attack] ← [Hit] ← [Stun]
```

상태 목록 (예시 enum):
```
Idle = 0,
Move = 1,
Attack = 2,
Hit = 3,
Stun = 4
```

FSM 핵심 규칙:
- 상태마다 고유한 행동이 있음
- 다른 상태로 전환되면 이전 상태의 행동을 중단하고 새 행동 시작
- HitState는 일정 시간 유지 후 Idle로 복귀
- 상태 우선순위 존재 (예: 이동 중 공격했는데 피격당해 스턴 → 스턴 종료 후 기본 상태로)

## 5. 아키텍처 모듈 구성

기획서에서 이미 아래 모듈 분리를 제안함:

1. **InputHandler** — 입력 처리기 (키 입력 감지, 커맨드 판정)
2. **StateMachine** — 상태머신 (FSM 관리)
3. **MovementController** — 이동 모듈
4. **CombatController** — 전투 모듈
5. **HitResponder** — 피격 리스폰더 (피격 반응 처리)
6. **Hitbox/Hurtbox 시스템** — 판정 생성/충돌 감지
7. **SpriteAnimationController** — 애니메이션 컨트롤러 (이동과 별개로 동작)
8. **CommandProcessor** — 지시/명령 처리기 (공격 시 상대에게 요구사항 전달)
9. **기술표 데이터베이스** — 엑셀 기반 기술 스펙 관리 (발생프레임/판정범위/효과)
10. **타이밍/프레임 동기화 모듈** — 우선순위 판정, 동시 입력 처리

## 6. 미확정/추가 논의 필요 사항

- 캐릭터별 스탯 차이가 어느 정도까지 있는지 (이동속도 외 체력, 데미지 등)
- 승패 조건 (라운드제? 체력 게이지?)
- 맵/스테이지 구성 (그리드 크기, 장애물 유무)
- 이미지 자료 반영 필요 (스프라이트, 캐릭터 디자인, UI 등) — 추후 v1.1에서 갱신 예정
